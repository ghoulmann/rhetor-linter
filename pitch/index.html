Documentation quality
you can measure
and ship.

A three-tool system that closes the gap between what your code does and what your docs say about it. Prose quality, structural coherence, and job coverage — measurable, trackable, visible across the org. No LLM required. No manual auditing.

Explore the tools Why this matters for AI →
The Stakes
AI assistants, RAG pipelines, and support bots ingest your documentation and use it to answer questions. Coverage gaps produce hallucination. Section size mismatches break retrieval. Terminology drift degrades embedding similarity. Stale docs produce confident wrong answers. These are not documentation aesthetics — they are the specific, peer-researched failure modes that cause AI-grounded systems to produce friction, dead ends, and wrong answers at scale. chancery-labs flags them at commit time, before any AI ingests the docs.

shela CLI Linter · CI Integration · Auto-fix
The Linter

Catches prose quality, structural violations, and coverage gaps on every commit. Text in, findings out — pure function, no state, no API key.

Vale rule types — load any --style-dir YAML set
10
Diataxis genres detected and scored separately
5
Quality dimensions: Clarity, Structure, Style, Form, Coverage
SH · 01
Prose Problems Invisible to Syntax Linters
Cohesion breaks, passive voice gaps, topic drift — none detectable without NLP. Standard linters miss all of it.
↗
SH · 02
RAG Chunking Failures
Sections too long get split mid-argument at ingestion. Sections too short have no retrieval signal. Doc structure is retrieval architecture.
↗
SH · 03
Coverage Gaps Found by Users, Not CI
No linter can flag what's missing without knowing what should exist. shela consumes a job manifest and flags unmapped jobs as lint findings.
↗
SH · 04
Voice and Terminology Drift
Different writers, different terms for the same concept. Non-inclusive language accumulates. Brand voice erodes commit by commit.
↗
SH · 05
Genre Violations
Concept docs with imperative steps confuse learners. ADRs without a Decision section are useless. How-tos with no verification step leave readers stranded.
↗
SH · 06
No Reliable Readability Signal
Flesch is gameable. Fog is noisy. No single metric is trustworthy enough to set CI thresholds against.

syla Quality Server · Dashboard · PR Gates · Badges
The Server

Makes shela's findings observable at repo and org scale. Trends, gates, alerts, badges, and a Backstage plugin — all from one stateful server that calls score_file() and stores the result.

Build phases: MVP → Dashboard → History → Auto-fix PRs

∞
Scan history — append-only, never overwrites, fully queryable

laxa JTBD Extractor · Coverage Auditor · Drift Detector
The Auditor

Reads the codebase — not the docs — and infers what the software does. Produces a job manifest that shela uses to flag coverage gaps before users find them.

~200
Library registry entries, SWEBOK-grounded, 0.90 confidence
4
Extraction signals: CI config, import graph, call patterns, docstrings
4
Taxonomy tiers: Ulwick ODI + DevOps + SWEBOK + Organizational
0
LLM calls required — core pipeline is fully rule-based
LX · 01
Nobody Knows What Jobs the Software Performs
No team has a complete, current, code-grounded map of what their software does from a user's or integrator's perspective.
↗
LX · 02
Integration Jobs Are Invisible
API surfaces, webhooks, SDK usage, and third-party integrations show up in support escalations, not in JTBD exercises.
↗
LX · 03
Manual JTBD Exercises Are Immediately Outdated
Workshop outputs and annotation sprints are accurate on day one and wrong by the next sprint. Code changes faster than any manual process.
↗
LX · 04
Coverage Audits Are Guesswork
Without a reliable job manifest, "do we have docs for this?" is an opinion. With laxa's manifest, it's a Jaccard score with a confidence level.
↗
LX · 05
Code-Doc Drift Undetectable Until It Hurts
Features ship, code changes, integrations get added — and the documentation never updates. The gap is invisible until a user, a new hire, or an AI assistant hits it.
↗
LX · 06
FAQ as a Gap Signal Nobody Reads
FAQ pages are a map of what users couldn't find in the main docs. laxa parses FAQ questions as JTBD signals, classifies them, and flags the ones that reveal undocumented jobs.
